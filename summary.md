# Підсумок: що зроблено, перевірено і не зроблено

## Зроблено

### Обовʼязкові функції

| № | Функція | Стан |
| --- | --- | --- |
| О1 | Підключення до Syrve: токен з автооновленням, пошук організації й програми, доступи лише в `.env` | ✅ |
| О2 | Реєстрація в Telegram: контакт → імʼя → гість у Syrve + програма + картка, без дублів за телефоном | ✅ |
| О3 | Номер картки, QR і баланс у боті | ✅ |
| О4 | Адмін-панель: вхід за логіном/паролем, пошук гостя за телефоном | ✅ |
| О5 | Нарахування/списання з причиною, заборона списати більше за баланс, журнал операцій | ✅ |
| О6 | Сповіщення в Telegram про зміну балансу (з панелі й з кабінету Syrve), одна операція — одне повідомлення | ✅ |

### Додаткові функції

- **Д1** — історія операцій (журнал і сторінка гостя);
- **Д2** — список гостей: пошук, фільтри, сортування, пагінація, створення й редагування;
- **Д9** — статистика за період (гості, нараховано/списано, графік по днях);
- **Д10** — ролі `власник` / `менеджер` і журнал дій адмінів.

### Понад завдання

- **Лендінг на `/`** — примітивна сторінка продукту, щоб вийшов повний життєвий цикл: сторінка продукту → вхід у панель → робота з гостями → бот.

### Технічні вимоги

- Запуск однією командою: `docker compose up --build` (`db` + `app`), міграції застосовуються на старті;
- зміни структури БД — лише міграції (`apps/api/prisma/migrations`);
- секрети лише в `.env`, у репозиторії тільки `.env.example`; в історії git ключів немає.

## Перевірено

**Автоматично** (Vitest, `npm run test`, 85 тестів, плюс `tsc --noEmit`):

- токен Syrve: кеш, оновлення, повтор при 401, один refresh одночасно;
- реєстрація: без дублів за телефоном, повторний виклик після збою, привʼязка гостя, створеного з панелі;
- нормалізація телефонів;
- операції: сума > 0, ліміт, причина, неможливість списати більше за баланс, `pending → done/failed`;
- worker сповіщень: дедуплікація, baseline, повтори відправки, помилка 403, відсутність Telegram;
- ролі й права, керування працівниками (не лишити систему без власника), журнал дій;
- пошук гостей і статистика.

**Збірка й запуск у Docker:** `docker compose build` і `docker compose up` на стеку з `.env`; міграції застосовуються (у тому числі остання), у логах «Syrve готовий», «Telegram-бот запущено», «Worker запущено»; `/health` повертає `ok`, лендінг і `/admin/login` віддаються.

**Вручну на тестовій організації Syrve** — сценарії з розділу «Як перевірити» у [README.md](README.md): реєстрація в боті, картка й баланс, пошук і операції в панелі, сповіщення про зміну балансу.

## Не зроблено і чому

- **Окремий режим-імітатор Syrve (mock) і dev-прокладка.** Вирішив не створювати власну прокладку, коли є готовий тестовий контур від Syrve. Сервіс працює безпосередньо з тестовою організацією, а `SyrveClient` має одну реалізацію. Наслідок: без `SYRVE_API_LOGIN` сервіс не стартує, а завдання допускало демо й без доступу до Syrve.
- **Apple Wallet / Google Wallet (Д8).** Google Wallet неможливо перевірити без змоги протестувати додавання картки, а для Apple Wallet потрібен акаунт розробника Apple. Робити непротестовану функцію не став.
- **Telegram Mini App (Д3).** Не реалізовував свідомо: на мою думку, для цього сценарію він не дає відчутної переваги над ботом (картка, QR і баланс і так доступні в чаті в один дотик). Залишив як потенційне невелике доопрацювання для захисту разом з ШІ — підпис `initData` перевіряється на сервері, а Nuxt-застосунок уже є.
- **Масштабування worker.** Syrve не має методу «усі транзакції» чи «усі гості», тому worker опитує транзакції по кожному гостю окремо. Для прототипу з десятками гостей це нормально; для тисяч знадобилося б розбиття або віддавати частину роботи подіям Syrve.

## Відомі обмеження прототипу

- Стан «чекаємо імʼя» під час реєстрації в боті зберігається в памʼяті процесу — після рестарту гість надсилає контакт заново.
- Дефолтні `admin/admin` і `user/user` призначені лише для швидкої перевірки; їх можна замінити в `.env`.
- Swagger `/docs` доступний без авторизації (описує лише API панелі, яке саме вимагає вхід).
- `nuxt typecheck` повідомляє про кілька неточних типів у фронтенді (збірка й робота не страждають).
- Файли `AI_LOG.md` і `CLAUDE.md` — окремо.
