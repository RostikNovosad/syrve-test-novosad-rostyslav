# Архітектура

## Загальна схема

```
Telegram ⇄ grammY (бот, long polling) ─┐
Адмін-панель (Nuxt SPA) ⇄ REST ────────┼─> логіка ─> SyrveClient ─> Syrve Cloud API
Worker (періодичний опит) ─────────────┘      │
                                              └─> Postgres
```

Усе працює **в одному процесі Node.js** (контейнер `app`) і одній БД (контейнер `db`). Окремих сервісів для бота, API чи worker немає — це модулі одного застосунку. У `docker-compose.yml` два сервіси: `db` і `app`.

## Частини сервісу

| Частина | Де | Що робить |
| --- | --- | --- |
| API та статика | `apps/api/src/app.ts`, `admin/` | Fastify: REST для панелі (`/api/admin/*`), `/health`, Swagger `/docs`, віддача зібраної адмінки з fallback на `index.html` для клієнтських маршрутів |
| Клієнт Syrve | `apps/api/src/syrve/` | `RealSyrveClient` — єдина точка виходу до Syrve; `TokenProvider` — токен з автооновленням; `discoverSyrve` — пошук організації й програми |
| Бот | `apps/api/src/bot/` | реєстрація (контакт → імʼя), картка з QR і балансом |
| Адмін-логіка | `apps/api/src/admin/` | сесії, ролі, операції з бонусами, пошук гостей, статистика, журнал дій |
| Worker | `apps/api/src/worker/notifications.ts` | збирає транзакції з Syrve, зберігає їх для статистики, кладе сповіщення в outbox і відправляє |
| Адмін-панель і лендінг | `apps/admin` | Nuxt 3 + Nuxt UI, режим SPA, `nuxt generate` → статика |
| БД | `apps/api/prisma/` | Postgres 17, Prisma, зміни схеми — лише міграціями |

## Що зберігаємо ми, а що беремо з Syrve

**Syrve — джерело істини** для всього, що стосується лояльності:

- гість (імʼя, телефон) і його ідентифікатор;
- картки гостя;
- програма лояльності та гаманець (бонусний рахунок);
- **баланс** — читається з Syrve щоразу, коли потрібен, і ніколи не кешується;
- транзакції гаманця.

**Наша БД** зберігає лише те, чого в Syrve немає або що потрібно для роботи обгортки:

| Таблиця | Навіщо |
| --- | --- |
| `guests` | звʼязок Telegram ↔ гість Syrve (`telegram_id`, `syrve_customer_id`), телефон (унікальний), імʼя, номер картки, курсор `last_revision` для опитування транзакцій. Telegram необовʼязковий — гостя може створити адмін |
| `admin_users` | логін, bcrypt-хеш пароля, роль (`owner`/`manager`), активність |
| `bonus_operations` | журнал ручних операцій з панелі: хто, коли, скільки, чому, статус `pending → done/failed`. Містить знімок імені й телефону гостя, щоб журнал читався без запитів до Syrve |
| `audit_log` | системні дії адмінів (входи, зміни гостей і працівників) |
| `notifications` | outbox сповіщень у Telegram зі статусом і кількістю спроб |
| `processed_transactions` | id вже оброблених транзакцій Syrve — дедуплікація |
| `loyalty_transactions` | копія транзакцій гаманця Syrve для статистики (агрегація по днях без запитів до Syrve) |

Копія транзакцій — це історичний факт, а не баланс: баланс із неї не обчислюється.

## Обмін даними з Syrve

Усі виклики — `POST https://api-eu.syrve.live/api/1/<метод>` з `Authorization: Bearer <token>`.

- **Токен:** `access_token` за `apiLogin` (ключ лише в `.env`). Кешується, оновлюється за 5 хвилин до спливу (життя 1 година); при відповіді 401 токен скидається й запит повторюється один раз; паралельні оновлення зливаються в один запит.
- **Організація й програма (О1):** `organizations` та `loyalty/syrve/program` на старті, результат кешується (помилка не кешується).
- **Реєстрація (О2):** `customer/info` за телефоном → `customer/create_or_update` → `customer/program/add` → `customer/card/add`. Кожен крок виконується, лише якщо потрібен, тому повтор після збою не створює дублів.
- **Картка й баланс (О3, О4):** `customer/info` (`walletBalances`, `cards`).
- **Нарахування/списання (О5):** `customer/wallet/topup` і `customer/wallet/chargeoff`. Перед списанням баланс перевіряється свіжим запитом.
- **Сповіщення (О6):** `customer/transactions/by_revision`.

Особливості Syrve, що вплинули на дизайн (деталі в [docs/syrve-notes.md](docs/syrve-notes.md)):

- Немає методу «список усіх гостей» — тому список гостей будується з нашої БД, а worker опитує транзакції по кожному гостю окремо.
- `by_revision` працює **по одному гостю**. Знак `sum` у відповіді не описаний, тому зміна рахується як `balanceAfter − balanceBefore`.

## Обмін даними з Telegram

- **Бот:** grammY, **long polling** — не потрібні ні домен, ні HTTPS, ні публічна адреса. Стан «чекаємо імʼя» тримається в памʼяті процесу (після рестарту гість просто знову надсилає контакт).
- **Сповіщення:** виключно `sendMessage` від worker. Бот реєструє гостя за контактом, який належить самому користувачу.

## Сповіщення про баланс (О6) — як працює

1. Раз на `NOTIFY_INTERVAL_SECONDS` (20 с) worker проходить по гостях і викликає `by_revision` від збереженої `last_revision`.
2. Нові транзакції гаманця нашої програми: зберігаються в `loyalty_transactions` (статистика); для гостів із Telegram додається запис в `notifications` (outbox). Транзакція позначається в `processed_transactions`; курсор рухається в одній транзакції БД з цими записами.
3. Окремо worker відправляє `pending` сповіщення: успіх → `sent`; помилка → повтор до 5 спроб; 403 (гість заблокував бота) → одразу `failed`.

Чому так:

- **Лише worker, а не панель.** Операція може бути зроблена в панелі, у кабінеті Syrve чи на касі. Якщо сповіщати з панелі, інші джерела лишаться без повідомлень, а операції з панелі — з дублями. Один шлях дає однакову поведінку і «одна операція — одне повідомлення».
- **Outbox + дедуплікація по id.** Збій відправки не втрачає сповіщення, а повторний прохід не дублює.
- **Baseline.** Для нового гостя перший прохід не розсилає стару історію: сповіщаються лише операції, зроблені після його появи у нас.
- **Один прохід за раз:** наступний тік не стартує, поки триває попередній.

## Адмін-панель: безпека

- Вхід за логіном і паролем (bcrypt), сесія — підписаний (HMAC) токен у httpOnly cookie `SameSite=Strict`, без стану на сервері; термін 8 годин.
- Rate-limit на вхід (5 спроб за хвилину); вирівнювання часу відповіді для неіснуючого логіну.
- CSRF: `SameSite=Strict` + обовʼязковий заголовок `x-requested-with` на всіх змінюючих запитах.
- Ролі: `owner` — усе; `manager` — гості та журнал операцій. Перевіряються на сервері (`403`), а не лише в інтерфейсі.
- Невдала операція з бонусами не губиться: запис у журналі лишається зі статусом `failed` і текстом помилки.

## Чому такий стек

| Вибір | Причина |
| --- | --- |
| Node.js 20 + TypeScript | один мінімальний стек для бота, API, worker і фронтенду; типи для відповідей Syrve |
| Fastify | легкий, схеми запитів (валідація), `inject()` для тестів, один процес тримає API, бота й worker |
| grammY | зручна типізована бібліотека для Telegram; long polling не вимагає інфраструктури |
| Nuxt 3 (SPA) + Nuxt UI | готові компоненти й українська локаль; `nuxt generate` дає статику, яку віддає той самий Fastify — окремий сервер для фронту не потрібен |
| Postgres + Prisma | міграції з коробки (`migrate deploy` на старті), типобезпечні запити, транзакції для курсора й outbox |
| Один контейнер `app` | завдання запускається однією командою; бот, API і worker мають спільну логіку й конфігурацію, окремі контейнери додали б складності без користі |
| Баланс не кешуємо | Syrve — джерело істини; зміни можуть прийти з кабінету чи каси, кеш давав би застарілі цифри |
| Docker `node:20-slim` | Prisma потребує openssl/glibc, на alpine працює нестабільно |
